# Commit

Use any hint supplied with the invocation or current request. Inspect the branch and origin with `git symbolic-ref -q --short HEAD` and `git remote get-url origin` before proceeding.

**Read the git conventions first** (`<base directory>/../git-conventions/SKILL.md`): it says how to find the default branch, which remote to push to, and which repos are personal.

Find the default branch as the git conventions show. Below, `<base>` is the result (for
example `origin/main`) and `<default>` is the branch name without `origin/`. Check whether the
repo is personal: in a personal repo, committing on the default branch is fine.

## Rules

- **The user reviews every commit before it's made.** Show the files and the proposed message, then ask for approval and wait. Don't rely on a permission dialog as the approval: in auto mode there may not be one.
- Sign off every commit with `-s`.
- Commit only on a feature branch, unless the repo is personal. If on `<default>` in any other repo, create a branch first (Workflow step 2); nothing lands directly on someone else's default branch.
- Linus Torvalds style:
  - Imperative-mood subject, ≤ 72 chars, lowercase unless naming a symbol: `fix race in worker pool shutdown`, not `Fixed a race condition`.
  - Blank line, then a body that explains why (motivation, constraint, intent). The diff already shows the what, so don't restate it. Skip the body when the subject is self-evident; terse is the goal.
  - Hard-wrap the body at ~72 columns with real newlines rather than relying on the editor or terminal to soft-wrap. The subject is never wrapped. Trailers stay one per line, unwrapped. Let a URL overflow on its own line rather than splitting it.
- Final trailer, after `Signed-off-by`:

  ```
  Co-Authored-By: Claude <model> <noreply@anthropic.com>
  ```

  `<model>` is the running model's name from the system context; never guess it.
- Plain prose: no marketing language, emojis, or `Generated by` lines, and no `feat:`/`fix:` prefixes unless the repo's `git log` clearly uses them.

## Workflow

1. Survey. Run in parallel:

   ```sh
   git status
   git diff
   git diff --staged
   git log -5 --oneline
   ```

   Read the recent log to match the repo's voice (capitalization, prefix conventions, length).

2. Ensure a feature branch. In a personal repo, skip this step and commit where you are. Otherwise, if the branch is `<default>`: tell the user, run `git fetch origin`, propose a branch name based on the changes (or ask for one), then create it off the freshly fetched upstream:

   ```sh
   git checkout -b <name> <base>
   ```

3. Draft the message: subject; body only if needed, explaining why (the bug, constraint, or design decision driving the change); trailers `Signed-off-by` (added by `-s`) and `Co-Authored-By`, no others.

4. Present the files that will be staged (from `git status`) and the proposed message in a fenced block, then ask:

   > Commit this? Reply **yes** to commit, **edit** with changes, or **stop** to cancel.

   Wait for the reply. On **edit**, revise and present again. On **stop**, leave everything unstaged and stop. Only **yes** moves on to step 5.

5. Commit, passing the message via a heredoc so the body and trailers format correctly:

   ```sh
   git add <files>
   git commit -s -m "$(cat <<'EOF'
   <subject>

   <body>

   Co-Authored-By: Claude <model> <noreply@anthropic.com>
   EOF
   )"
   ```

   With no body, drop the body block but keep a blank line between the subject and the trailer. Confirm with `git log -1 --oneline`.
