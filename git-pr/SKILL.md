# PR

Before proceeding, inspect the branch and remotes with `git symbolic-ref -q --short HEAD` and `git remote`.

## Rules

- **The user reviews every PR before it's created.** Show the title and body, then ask for approval and wait. Don't rely on a permission dialog as the approval: in auto mode there may not be one.
- Open PRs ready for review, not as drafts.
- Body shape: a short preamble (1–2 paragraphs: the context, bug, or constraint, and a succinct description of what the PR does, why more than what), then a `Key changes:` bullet list. Each bullet is one line shaped `**Short label**: detail`, covering one distinct change with its one-clause rationale. A trivial single-change PR may stay preamble-only. No headings, no fluff.
- Leave out any "Test plan" section, even as an empty checklist.
- Write each paragraph and bullet as a single line and let GitHub soft-wrap; manual line breaks render literally and look ragged.
- Footer is exactly `Assisted by Claude <model>` on its own final line, where `<model>` comes from system context rather than guessing. The body carries no "Generated by", robot-emoji, or Co-Authored-By markers.
- Print the PR URL on its own line after creation so the user can click through.

## Workflow

1. Survey. **Read the git conventions first** (`<base directory>/../git-conventions/SKILL.md`): it says how to find the default branch, which remote to push to, and which repos are personal. Find the default branch as it shows.

   Below, `<base>` is that result (for example `origin/main`) and `<default>` is the branch name without `origin/`. If the current branch is `<default>`, stop: there's nothing to open a PR from.

   - **Head remote:** the first that exists, in the git conventions' order, the same as the `git-push` skill.
   - **Base repo:** `<owner>/<name>` from `git remote get-url origin`. The PR always targets origin, even when the branch lives on a fork.
   - **Head ref:** `<branch>` when the head remote is `origin`; otherwise `<fork-owner>:<branch>`, with `<fork-owner>` taken from the head remote's URL.

   Then run in parallel:

   ```sh
   git status
   git log <base>..HEAD --oneline
   git diff <base>...HEAD
   git ls-remote --heads <head-remote> <branch>
   gh pr list --repo <owner>/<name> --head <branch> --state open --json number,url,headRepositoryOwner
   ```

2. Check it's ready:

   - **Pushed and up to date:** `git ls-remote` must return a SHA equal to `git rev-parse HEAD`. If the branch is missing on the head remote, or the SHA differs, tell the user to run `/git-push` first; this skill doesn't push.
   - **No PR already open:** if `gh pr list` returns an open PR whose head owner matches, print its URL and stop.

3. Draft. Title ≤ 72 chars, imperative; mirror the lead commit's subject when it captures the whole PR, otherwise summarize the set, following the repo's title conventions from `git log`. Body per the rules above, explaining why the change is needed and what the PR does, without restating the diff.

4. Present the title and body in a fenced block, along with the base repo, base branch, and head ref, then ask:

   > Open this PR? Reply **yes** to create it, **edit** with changes, or **stop** to cancel.

   Wait for the reply. On **edit**, revise and present again. On **stop**, stop. Only **yes** moves on to step 5.

5. Create:

   ```sh
   gh pr create --repo <owner>/<name> --base <default> --head <head-ref> --title "<title>" --body "$(cat <<'EOF'
   <body>

   Assisted by Claude <model>
   EOF
   )"
   ```

6. Print the PR URL on its own line.
